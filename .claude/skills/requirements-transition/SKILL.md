# Requirements transition — execution (Stint)

Carry out a **prepared** requirements transition. The design work is done: the
grill interview happened, `requirements-transition.md` exists, the new docs and
mockups are authored, and the old docs coexist as `*-old.html`. This skill
turns that work-list into landed, verified, reviewed, evidenced code — then
swaps old→new and hands the human one PR to merge.

**Scope: execute, don't redesign.** The work-list and the new docs are the
contract. If executing surfaces a genuine design gap (a contradiction between
rows, a missing decision), stop and ask the user — never invent requirements
mid-run. Small implementation choices within a row's stated intent are yours.

Read first:

- `requirements-transition.md` — the work-list. §0 is its own consumption
  legend; §1 the signed-off global decisions; §2 the per-section requirement
  tables (ID, Change, Core `●`, Surfaces, Files, Mockup, AC, Rec `▶`); §W the
  recording scope; §R the two reviews; §Z the swap list.
- `CLAUDE.md` and `context/process.html` — repo conventions and the process
  principles this run must not violate (stay green, evidence must not drift,
  timeless docs, scaffolding is deleted when consumed).
- The new docs (`context/prd.html` etc.) and every mockup named in the
  work-list's Mockup column.

## Standing rules (the whole run)

- **Stay green.** `npm run build && npm test` is green at every checkpoint;
  never advance a wave on red.
- **Checkpoint per wave.** Commit after each green wave with a message naming
  the wave and requirement ids — the run stays resumable and bisectable.
- **Never weaken a gate.** Update tests to assert new intended behavior; never
  delete or loosen an assertion to get to green. Evidence is regenerated by
  the suites, never hand-edited.
- **One PR, never merge.** All work lands on the current working branch and
  its single PR. The human gate is the merge.
- **Honest reporting.** A stage that cannot run (missing host capability,
  impossible recording) is reported precisely, never faked.

## Choosing subagent model level

Fan work out to subagents (the Agent tool). Each subagent runs at a **model
level** — `haiku` < `sonnet` < `opus` < *inherit* (omit `model`; the session's
own model, the strongest available). Decide per task, by this procedure:

1. **Default is inherit.** Downgrading is a deliberate act, never the reflex.
2. **Ask the gate question:** *if this subagent does its job subtly wrong,
   what catches it?*
   - A **deterministic gate** catches it — the build, a test, a golden, the
     judge, the evidence-drift comparison, or a later stage that mechanically
     rechecks the output — then the task is downgrade-eligible.
   - Only a **review or a human** would catch it — do not downgrade.
3. **Downgrade-eligible tasks, by kind:**
   - `haiku` — mechanical and fully specified, verified by command: run a
     suite and report the failures verbatim; regenerate evidence; apply an
     exact rename list; convert a file format; collect an inventory a later
     stage rechecks.
   - `sonnet` — well-scoped implementation against a precise contract with
     co-located tests that pin the behavior; scoped searches whose findings a
     stronger reviewer then verifies.
4. **Never downgrade:** anything that authors or alters requirements or
   acceptance criteria; any core (`●`) integrity/data-loss requirement; the
   two review stages; repair work whose cause is not yet understood; any task
   that decides what the spec *means* rather than carrying out what it says.
5. **Reasoning effort follows the same rule** — low for mechanical
   run-and-report steps, high for reviews and repairs.
6. **When in doubt, inherit.** A wrong cheap agent costs a diagnose-and-repair
   loop that dwarfs what the downgrade saved.

The same question — *what catches a subtle failure?* — also decides how much
context a subagent gets: every implementer receives the work-list row, its
mockup(s), the relevant new-doc sections, and the standing rules above.

## Stage 0 — Preflight

1. Confirm the tree is green (`npm run build && npm test`) before touching
   anything; a pre-existing red is the user's to know about, not yours to
   absorb.
2. Read the whole work-list. Confirm every row has the columns §0 declares and
   every named Mockup file exists. A malformed work-list goes back to the user
   (or to the change-requirements skill), not into improvisation.

## Stage 1 — Plan

For each requirement row, produce a short plan: the exact file set it will
touch, the implementation approach, the AC it must land (per its AC column:
BDD / PROP / GOLD / JUDGE / MANUAL), and the evidence it must show up in.
Subagents may research in parallel (read-only; `sonnet` is usually right —
Stage 2's implementers and the gates recheck everything).

Then schedule rows into **file-disjoint waves**: no two requirements in a wave
may touch the same file. Order waves by dependency (schema/core → CLI/GUI →
docs/criteria). DELETED rows usually land late, next to the swap.

## Stage 2 — Implement in waves

Per wave: one subagent per requirement (model level per the rubric), each
owning its declared files exclusively. Every implementer also lands/updates
the co-located tests its AC column demands. After the wave: run
`npm run build && npm test`; repair on red (inherit-level subagent — the cause
is unknown by definition) before the checkpoint commit. Then the next wave.

## Stage 3 — AC verification

Regenerate all evidence, serialized: `npm run build`, `npm test`,
`npm run verify:no-network`, `npm run judge`, `npm run evidence`. Every
requirement must be covered by a **passing, executable** AC of its mapped
method(s) — no stubs, no skips. MANUAL-method rows get their runbook entry and
its cheap automated mirror (process principle R03).

## Stage 4 — The two reviews + improvement loop

Run both reviews (§R), each as its own subagent at inherit level:

1. **AC-evidence-sufficiency review** — an adversarial completeness critic per
   requirement. Defaults to *insufficient*; upgrades only if the requirement
   is implemented **and** covered by a passing AC of its mapped method **and**
   visible in the regenerated evidence.
2. **Code-quality & architecture review** — Matt Pocock
   *improve-codebase-architecture* lineage: shallow modules, leaky seams, poor
   locality, cognitive bounce, duplication; apply the deletion test; rate
   findings `Strong` / `Worth exploring` / `Speculative`.

Then a **bounded improvement loop** (2–3 rounds): apply the insufficiencies
and `Strong` findings, re-run Stage 3, re-run the failed review. Findings that
are wrong or too risky are skipped *with a stated reason*, not silently.

## Stage 5 — Screen-recording QA (runs LAST)

QA evidence, not executable AC — capture only after AC and both reviews are
clean, so the recordings show the shipped UI. Scope (§W): every core (`●`) GUI
row, every Rec `▶` row, and code-change-adjacent requirements demonstrable in
the GUI.

Conventions (a `haiku`/`sonnet` task once the recipe list is confirmed — the
output is a visible artifact the PR embeds):

- Drive the real renderer via the record harness:
  `node packages/gui/judge/record.mjs --list` for recipe ids, `npm run record`
  or per-recipe runs to produce `.webm` (gitignored scratch).
- Convert to **committed, ASCII-named GIFs** under
  `acceptance/evidence/recordings/` (`§12 R15` → `12-r15.gif`), slowed ~0.5×
  with a ~1.5 s end-frame hold, two-pass palette:

  ```
  ffmpeg -y -i in.webm -vf "setpts=2.0*PTS,fps=15,scale=iw:-1:flags=lanczos,tpad=stop_mode=clone:stop_duration=1.5,palettegen=stats_mode=diff" pal.png
  ffmpeg -y -i in.webm -i pal.png -filter_complex "setpts=2.0*PTS,fps=15,scale=iw:-1:flags=lanczos,tpad=stop_mode=clone:stop_duration=1.5[v];[v][1:v]paletteuse=dither=sierra2_4a" out.gif
  ```

- Make interaction visible (synthetic cursor + click pulse). Update the
  recordings index (`acceptance/evidence/recordings/README.md`).
- A recording the host genuinely cannot capture is listed as NOT CAPTURED with
  the reason — never fabricate a file.

## Stage 6 — One PR

Final serialized evidence regen (Stage 3 commands), commit, push the working
branch, and create/update the **single** PR: a per-requirement checklist from
the work-list, the two review outcomes, the evidence booleans, and each GIF
embedded inline — `![<req id> — <caption>](<raw-url-pinned-to-commit-SHA>)` —
with a one-line caption. Do not open a second PR; do not merge.

## Stage 7 — Gated swap / cleanup

Only when every requirement has passing AC evidence **and** both reviews are
clean, perform the old→new swap inside the same PR (§Z):

- Delete the `*-old.html` docs.
- Delete GUI files retired by DELETED rows.
- Delete **`requirements-transition.md`** itself — the work-list is consumed
  scaffolding.
- Ensure `README.md`, `CLAUDE.md`, `acceptance/criteria/COVERAGE.md`, and
  `acceptance/criteria/parity-matrix.json` reference only the new docs and
  entities; no change-narrative residue anywhere (timeless docs).

Final commit + push; refresh the PR body. **The human gate is the merge.**

## Definition-of-done checklist

- [ ] Preflight green; work-list validated against its own §0 legend.
- [ ] Every row planned (files, approach, AC method, evidence) and scheduled
      into file-disjoint waves.
- [ ] Each wave landed green with a checkpoint commit; no weakened assertions.
- [ ] All evidence regenerated; every requirement has a passing executable AC
      of its mapped method(s).
- [ ] Both reviews run; improvement loop applied; skipped findings justified.
- [ ] §W recordings captured LAST as committed inline-embedded GIFs (or
      honestly reported NOT CAPTURED); recordings index updated.
- [ ] One PR with checklist, review outcomes, evidence, inline GIFs.
- [ ] Gated swap done: old docs, retired files, and the work-list deleted;
      front-door docs reference only the new state.
- [ ] Subagent model levels chosen per the rubric (gate question), not by
      habit.
