Engineering Requirements & Conventions · v1

prd.html specifies the product; process.html specifies the apparatus that proves it. This specifies the code and tests themselves — the judgment calls no gate can check: how much to build, how much to test, how to write what gets built.

The primary reader is the agent session writing code (process.html §03). The default failure mode of such a session is not sloppiness but over-delivery: extra abstraction, speculative flexibility, tests for cases that cannot occur — all of which pass every gate and compound silently. Most of this doc exists to calibrate that balance. Content is distilled from the named external sources (§09) and vendored: guidance that lives only at a URL cannot bind an offline session.

01 Scope

A third kind of requirement

Application requirements say what the product does. Process requirements say how it is built, verified, and released. This doc holds the third kind: how the source is written — design judgment, style, test craft. Everything here binds at recorded-convention tier (process.html §08) unless marked as a requirement in a labeled block; there is exactly one such block (§03, test integrity), because only it can produce a false green.

One home per fact still rules: acceptance.html owns which method proves a criterion; this doc owns whether and how code and tests get written at all; glossary.html owns the domain words that name things; architecture.html owns the runtime shape the code lives in.

02 Balance

Engineering balance

Under-engineering fails visibly — gates go red, behavior is wrong. Over-engineering passes everything and is only caught by judgment, so the rules below lean against it. The vocabulary is the deep-module school: a module is judged by the ratio of behavior delivered to interface imposed; a shallow module's interface costs more than its implementation saves; a seam is where behavior can be observed or replaced without reaching inside.

  • Every changed line traces to the request. Behavior nobody asked for is scope creep — a review defect even when the code is correct. Say "considered X, chose not to build it" instead of building it.
  • A presumptive capability has four costs: build, delay (what didn't ship instead), carry (every future reader pays it), repair (the guess was probably wrong anyway). YAGNI wins even when the guess is right, because carry and delay were paid regardless. YAGNI never excuses skipping refactoring or tests — those keep change cheap; skipping them is debt, not thrift.
  • Modules deep, not many. Much behavior behind a small interface. Both extremes fail: the god module is unmanageable, but splitting further once interfaces dominate subtracts value. Two functions that can only be understood by flipping between them are one function — merge them back.
  • Duplication is cheaper than the wrong abstraction. Copy on the second occurrence; abstract on the third only if the copies have been changing in lockstep. Inside a wrong abstraction (parameters and conditionals accreting per caller), the fastest way forward is back: re-inline into every caller, delete each caller's dead branches, then see what abstraction — if any — remains.
  • Prefer fixes that delete structure. The best structural fix removes the condition that let the defect exist; a fix that adds a layer, a knob, or a guard for callers who may never come is usually the wrong one.
  • Design it twice. For a nontrivial interface, sketch two genuinely different shapes before committing; record the rejected shape where the decision lands (PR body or file-header comment). Prefer the somewhat-general interface — one insert(text) over three key-specific mutators — when it is deeper, not merely bigger.
  • Simple-design priority order: passes the tests > reveals intention > no duplication > fewest elements. Never satisfy a lower rule by sacrificing a higher one — deduplication that obscures intent is a net loss.

Match investment to subdomain

Design and test effort follow the subdomain, not the file that happens to be open:

TierStint membersTreatment
coreEntry/timer state transitions, invariants, merge/gap/sleep resolution, report & rounding math (@stint/core).Deep design, thorough tests, glossary-exact names.
supportingSettings, CSV/JSON export shaping, tray/window plumbing, favorites.Built plainly. Straight-line code is correct here, not shameful.
genericSQLite, Electron, packaging, the update mechanism.Adopted, configured, never re-invented.

Applying core-tier patterns to supporting code is the named form of gold-plating — an event-sourced settings store is the canonical violation.

03 Balance

Testing balance

Which code deserves tests is decided by two axes — domain significance/complexity, and collaborator count — not by coverage or by mirroring source files:

CodeStint membersTesting
Domain logic, few collaboratorscore transitions, invariants, report math; the Electron-free gui/src projections.Unit-test thoroughly — highest value per test, cheapest to keep.
Glue, many collaboratorsCLI command handlers, ipc-handlers.ts, main.ts wiring.Few integration tests over real seams — the longest happy path plus what units can't reach.
TrivialGetters, pass-through mappers, constant tables.None. A test here is pure carry cost.
Complex glue(none tolerated)Don't mock it into testability — split it into domain + glue. Untestability is a design smell.
  • Stopping rule: write a test where a failure would be scary; stop when enumerating further cases is boring. Boredom is the signal that marginal cases carry no information.
  • Don't test what can't break: the compiler's job (a wrongly-typed input is not a test case), the standard library, SQLite, Electron itself.
  • Don't add a test that duplicates another test's failure conditions; asserts a mock was called; computes its expected value by the same algorithm as the code (tautological); or exists to raise a coverage number. Coverage is a gauge, never a target — targets get gamed.
  • Deleting a test is a legitimate move when it never fails, fails only on refactors, or pins behavior that is gone — subject to the requirement below.
  • Apparatus is code with a budget. A new guard must name the defect it catches; a guard whose defect costs less than the guard's upkeep is over-testing. This is the counterweight to process.html R03/R05, which only push toward more apparatus.
Requirement — test integrity Never weaken an assertion, delete or skip a test, or fit an expected value to observed output in order to reach green. Each of those is sometimes right — but only as a declared decision, named in the PR with its reason, never as a silent step of getting a suite to pass. A test quietly bent toward the code is a false green manufactured at the source.
04 Language

TypeScript

Style rules

  • Named exports only; minimize each module's export surface. No export let — mutable state goes behind functions.
  • Assertions are guilty until proven safe. as and ! need either a runtime check instead (instanceof, narrowing) or a comment proving why the assertion holds. @ts-ignore/@ts-nocheck: never. @ts-expect-error, with a reason: tests only. The kind is the point — @ts-expect-error fails once the error it suppresses disappears, so a suppression that has gone stale reddens; @ts-ignore suppresses silently forever. @typescript-eslint/ban-ts-comment is the gate.
  • any triad: prefer a precise type; else unknown; else the narrowest possible any hidden inside one well-typed function, with a comment saying why.
  • Throw only Error subclasses; catch as unknown; map to exit codes / user copy once, at the entry point (bin.ts), never mid-stack. Empty catch requires a comment naming what is deliberately swallowed (store.ts:210 is the house example).
  • Nullability lives at the use site. No |null/|undefined inside a type alias; optional fields (?) over |undefined; handle null where it arises, don't pass it along.
  • interface over object-literal type; union-of-literals over enum; T[] for simple element types; === always (== null allowed to cover both nils).
  • Inference discipline: no annotation on trivially-inferred initializers; annotate exported function signatures.

Type design

  • Types represent only valid states. The house example is the keystone idea itself: a running timer is the row whose end is null — the state is the shape, not a flag beside it. Prefer tagged unions to parallel optional fields; a type where two optionals can't both be set is lying about its states.
  • Parse, don't validate. Every edge — argv, DB row, IPC payload, settings JSON — starts as unknown and passes through one parser that returns a domain type carrying the proof. Past the edge, functions accept domain types and never re-check; scattered re-checking (shotgun parsing) lets bad data get discovered after side effects.
  • Name types in glossary language (glossary.html — one canonical term, no synonyms). Prefer precise types to naked string/number for domain values; consider brands where two ids can be confused.
  • Non-fatal outcomes are values, not exceptions: WriteResult<T>'s { value, warnings } is how "warned, not blocked" is typed. Exceptions are for refusals and faults only.
  • The store boundary maps representations: snake_case columns to camelCase domain fields via private row interfaces, in the store, once.
05 Tests

Test authoring

The four properties a test is judged by: protection against regressions, resistance to refactoring, speed, maintainability — multiplied, so any factor at zero zeroes the test. Resistance to refactoring is non-negotiable: a test that breaks on a behavior-preserving refactor is a false-alarm generator and erodes trust in red.

  • Test behaviors at public seams, not methods or internals. One behavior per test, named for the behavior. No test file mirrors a source file's function list.
  • Reach a package the way its consumers do. Core's tests import @stint/core, never ../src/<module>.js. A deep-path import pins a file location alongside the behavior, so moving a function breaks a test that should not care — and a module dropped from the barrel goes dark to both surfaces with its test still green.
  • Assert state and output, not interactions. Call counts, call order, and private state are implementation details; a test asserting them serves a third user — the test itself — that nobody ships to.
  • Mock only unowned boundaries. The SQLite file is a managed dependency — always real (Store.openMemory or a temp file), never stubbed. Time is already a seam (TT_NOW, the mutableClock fixture, page.clock) — use it; never sleep. Nothing in packages/* mocks another Stint module. The one unmanaged dependency is the update check's network edge — stub exactly that.
  • One pinned clock, spelled one way. A test whose subject touches time pins it: const NOW = new Date('…') at module scope, handed to the store as () => NOW — a Date, not a string re-parsed per call, so the seam is copy-pasteable between files without first checking what NOW is. Where the same instant is also needed in core's stored form (an atUtc argument, a read-back startUtc, TT_NOW on a subprocess env), NOW_UTC holds the literal and NOW derives from it. A clock that must move mid-test is the shared mutableClock fixture (core/test/support/clock.ts) — advance by a delta or set to an instant — never a per-file copy.
  • DAMP over DRY; no logic in tests. A test is readable start-to-finish without helpers hiding the cause–effect chain; expected values are literals from an independent source, never computed the way the code computes them. If a test needs a loop or a conditional, it is doing too much.
  • The ideal test never changes until the requirement it pins changes. Refactors, other features, and unrelated fixes should not touch it.
  • Flaky means fixed or deleted, never retried into submission — a suite that cries wolf stops gating anything.
  • Source-text guards are a last resort: a regex over source belongs only where the defect is invisible to a driven page (tray.test.ts, renderer-isolation.test.ts — no host exists under headless Chromium). A source regex breaks on a rename and passes on a bug; anywhere a JUDGE scene can see the behavior, the scene is the guard.

Whether code deserves a test at all is §03's table; which method proves an acceptance criterion is acceptance.html's routing rule. This section only governs how the resulting test is written.

06 Electron

Electron

The layering rule

Core owns every decision; gui/src owns Electron-free projections; main.ts stays thin wiring; the renderer owns chrome only. The renderer never re-derives what core can compute — it imports (su.ts bundles formatDuration, tagDiff from core and gui/src) rather than hand-mirroring. Where new logic goes:

The logic…Home
could serve both surfaces, or decides anythingpackages/core
is GUI-only but pure (a projection, a menu model, a label)gui/src/*.ts — Electron-free, unit-tested
needs an Electron APImain.ts — thin, delegating to the above
is display behavior onlyrenderer/*.js

This is the humble-object discipline that keeps §03's quadrants clean: what can't run under vitest is kept too thin to hide a decision.

Adding an IPC channel — the four-file ritual

One channel touches four files, and three bind tests catch a missed step (ipc-handlers.test.ts, qa-driver.test.ts, parity.test.ts). Do it in order rather than learning it from CI:

  • gui/src/ipc.ts — the channel name in CHANNELS (this generates the preload bridge).
  • gui/src/ipc-handlers.ts — the handler, delegating to core. There is no fifth file: the QA driver (gui/qa/driver.mjs) imports this map rather than porting it, so a new channel reaches a sweep with no second edit (issue #165).
  • acceptance/criteria/parity-matrix.json — the capability row.
  • cli/src/program.ts — the tt twin (parity is a requirement, not a hope).

Security posture

  • Never flip an isolation default: contextIsolation on, nodeIntegration off, renderer sandboxed. Most of the official checklist is "don't undo a default" — guarded here by renderer-isolation.test.ts.
  • Local-only content narrows the checklist. Stint loads only bundled HTML, so the remote-content items (permission handlers, navigation limiting, webview hardening) are N/A by construction — the no-network backstop (process.html R07) is what keeps that construction true.
  • Still live for a local-only app: the CSP in index.html; never exposing raw ipcRenderer through the bridge (only named CHANNELS wrappers); shell.openExternal only on vetted URLs; packaging-time fuses (runAsNode off in the shipped app — dev/test builds keep inspect fuses on because the tooling needs them).
  • Main is the UI broker — never block it. No sync IPC, no long work on the main thread, no polling where an event exists (powerMonitor, the DB file watcher).

Tray facts

  • Keep a persistent reference to the Tray or it is garbage-collected and the icon vanishes.
  • macOS: tray icons are Template images (iconTemplate.png + @2x) so the OS handles menu-bar inversion; setting a context menu suppresses click events — click-opens-popover and native-menu are exclusive per platform choice.
  • Linux: tray click behavior varies by desktop; never design Linux UX around left-click, and re-call setContextMenu after mutating a menu item.

Testing the Electron band

The harness strategy is settled: the JUDGE/QA harnesses drive the real renderer over real core in headless Chromium — faster and more deterministic than driving Electron itself, and the official custom-test-driver pattern is this approach's published ancestor. Playwright's Electron mode (still experimental upstream) is reserved for the thin band nothing else can reach — real BrowserWindow/Tray/preload wiring — which today is covered by static guards plus the MANUAL runbook. Don't migrate the harness to it.

Recorded traps

  • gui/tsconfig.main.json uses an explicit file list — a new gui/src module is invisible to the build until added there.
  • gui/judge/ and gui/qa/ were ESLint-exempt apparatus until issue #184 — the exemption was one languageOptions block away from unnecessary, and turning the linter on found five real defects. They now lint under browser+node globals like the renderer; the trap it left behind is that three separate findings (#165, #176, and #184's own) hid in that gap first.
07 Comments

Comments

House style is comment-dense — roughly a third of implementation lines, more in gui/src — but the density is a side effect, not the rule. The rule: a comment earns its place only by carrying what the code cannot.

  • Every module opens with a header stating what it owns and why it exists, citing the PRD section (§NN Rxx) and issues that shaped it.
  • Inline comments carry decisions, constraints, and warnings: why this ordering, why the obvious alternative is wrong, which incident this line answers (app.js's issue-#50 post-mortem at the site of the fix is the model). Cite §/R and #issue so the trail survives the session that knew it.
  • Never mechanics, never narration — not what the next line does, not where code was moved from, not why a change is correct (that is PR talk, dead the moment it merges).
  • The stopping rule: delete the comment mentally; if the code still tells the reader everything the comment did, it was noise. If deleting it loses a decision, it stays.
08 Gherkin

Gherkin

The features run against both surfaces, so declarative style is not taste — it is what makes parity provable. A step that names a widget, a flag, or a selector can only be true of one surface: a mechanism in a step is a parity bug by construction.

  • Steps state intent and outcome ("When I start a timer for Client A"), never mechanics ("When I click the tray button"). Mechanics live in the step definitions, once per surface.
  • One behavior per scenario — one When→Then pair; a second pair means a second scenario, with the earlier pairs demoted to Given-shaped seeding ("rename a pinned favorite" seeds the pin, it does not re-prove it). Every scenario runs twice (core + tt), so a bundled scenario hides that many behaviors behind one line of red. Healthy scenarios run 3–7 steps.
  • The deletion test decides the one exception (#356): delete every When→Then pair after the first. If the scenario's name still makes its claim, the later pairs were bundling — split. If the name no longer makes its claim, the pairs are one composition claim ("archive then restore round-trips"); keep them and name the composition. A name that enumerates actions ("create, rename then archive") is a list of claims, not a composition — split it. The test is mechanical so a reviewer can check it was run; a prose-judged exception is a rationalization template.
  • Enrollment: every kept multi-When-group scenario carries one line in features/when-groups.allowlist (file :: scenario name :: one-line justification). scripts/check-when-groups.mjs fails CI on any un-enrolled scenario with more than one When group — a When keyword starts a group; And/But steps riding it continue it and do not count.
  • Given is state, When is the one action, Then is observable outcome only. No assertions in Given/When; no actions in Then.
  • Key examples, not combinatorics: the smallest example set that pins each rule's boundaries; each scenario illustrates exactly one rule. Exhaustive tables are over-testing wearing a requirements hat — exhaustiveness is PROP's job.
  • No incidental detail: a name, a date, or a tag appears in a scenario only if the behavior depends on it.
  • Readable cold: a reader who has never seen the code understands the feature file, or it has failed as specification.
