Design · Calm · Warm Paper · normative · light mode

The visual system, as requirements. Colour, type, spacing, components, and the accessibility floors — each a rule a change can be checked against, not a vibe a change can drift from.

PRD §12 owns what the GUI does — views, behavior, layout topology. This doc owns how every surface looks: the tokens, the component grammar, and the numeric floors. The mockups under mockups/ illustrate this spec (PRD §18); where a mockup and this doc disagree, this doc wins. Values live in design.tokens.json — this doc names the rules, that file carries the numbers, and nothing else does.

01Tokens

One source of truth

D01Two layers. design.tokens.json (W3C DTCG format) holds primitive scales — Radix Colors light-mode sand, tomato, red, grass, amber, adopted wholesale — and a semantic layer aliasing one step each. Surfaces reference semantic tokens only; a raw scale step or hex literal in a mockup or the app is a defect.

D02Generated, never copied. A generator (scripts/gen-tokens.mjs) writes the CSS custom-property block between /* STINT-TOKENS */ markers in every mockup and in packages/gui/renderer/styles.css. Hand-editing inside the markers is a defect; a guard test asserts the generated blocks match the tokens file and stays wired (process.html — protect the guard).

D03Room for dark. The scales carry documented dark counterparts upstream; v1 ships light-only. Dark mode is a tracked opportunity, not a partial presence — no dark token may ship before the whole mode does.

02Principles

Calm · Warm Paper

Six principles govern every rule below. Built on Fluent 2's discipline — light, depth, motion, material, scale — with the showy parts dialed off for a calm, local, single-user tool.

  • One rationed accent on a quiet canvas. Near-neutral surfaces; the clay accent marks the one thing that matters in a view — its primary action and the live running state. A signal, never decoration.
  • Depth, not tint. A region rises by a soft shadow alone, never a coloured or bordered box. One elevation ladder; never nest cards.
  • The UI speaks for itself. Every element earns its pixels; when shape, position, or state carry the meaning, the words go.
  • Small type ramp, tabular time. Hierarchy from size + weight, never colour or italics; every clock and duration in tabular numerals.
  • Spacing on the grid, generous air. Every pad, gap, and margin on the 4px grid (§05); radii a fixed trio.
  • One control per choice-shape. Toggle = on/off · segmented = ≤4 exclusive peers · select = many. Line icons only — never emoji.

05Layout

Grid, radii, elevation

D07Spacing grid. Every padding, gap, and margin is a multiple of 4px, with 2px permitted as the sub-4 half-step (legal: 2, 4, 8, 12, 16…). Component intrinsic heights are free (a 34px button is legal; its 11px side padding is not — that's 12px). Alignment comes from the grid, not from per-view pixel nudging.

D08Radius trio. 8px controls · 12px cards · 16px window & overlays. No fourth radius. Recorded exemption: a functional mark whose control radius would exceed half its own box — the calendar corner checkbox and the progress-bar track — keeps 4px, because rounding further changes what the control reads as (a circular checkbox reads as a radio). The exemption list is closed; a new sub-radius is a spec change, not a precedent.

D09One elevation ladder. canvas → card → raised → popover → modal (shadow.* tokens), plus the chip lift (shadow.chip) as the sub-card selection rung (D12). A surface sits exactly one rung above what it covers; depth is the only "this is a layer" signal — never a tint or decorative border.

D10Motion. State changes ~120ms; nothing moves without meaning; no parallax, no decorative transitions. Under prefers-reduced-motion, transitions collapse to instant.

06Components

Component grammar

D11Accent discipline. At most one accent-filled (accent-solid) primary action per view — the single most-likely action. Everything else is secondary (paper + border), ghost, or danger. Clickable text carries the neutral button treatment; inert text never does.

D12Selection ≠ accent. A chosen thing lifts — a raised paper chip with a shadow (the segmented idiom) — it does not turn accent. This includes the nav rail: the active item is a lifted chip whose icon may take accent; its label stays ink. (accent-weak backs non-selection accents only: pills, weak fills.)

D13Fields. One border (rule-strong), one radius (8px), one focus idiom: accent border + the 3px ring. Every field carries a visible label (this is also the §07 border-contrast exemption). Placeholder text uses muted, never faint.

D14Pills & tags are the only pill-shaped elements; their colour is semantic (run / flag / accent), never decorative.

D15Inline messages (PRD §12 R21): a warn advisory (flag tokens) is allowed-but-flagged — the write saved; an err (danger tokens) is a refused write — the form stays open, nothing changed. Two palettes so an advisory never reads as a hard block.

D16Icons. One line family (the #i-* symbol set), 1.6px stroke, currentColor; icons inherit text colour and take accent only when their item is active. Icon-only affordances use muted, never faint, and carry an accessible name.

08Verification

How this is verified

D17Two mechanisms, split by what each can honestly prove (process.html — green is meaningful):

  • Computed checks — token parity (generated blocks match design.tokens.json), the A01/A02 contrast floors over the permitted token pairs, and the reduced-motion guard. Cheap, exact, on the PR path.
  • Rendered comparison — composition, layout, and look-and-feel are judged against the mockups via the JUDGE apparatus over captured screenshots (acceptance/criteria/judge-rubric.md), including the A03/A04/A05 floors.

A mockup that has drifted from this spec is a bug (PRD §18). The per-view × per-state coverage of what gets rendered and judged lives in acceptance/criteria/STATES.md.

09The mark

The app's face in the OS

Everything above dresses surfaces Stint draws. This section covers the images the operating system draws for it — the launcher icon and the tray glyph — which no stylesheet reaches and no screenshot of the app contains.

D18The mark. Two back-to-back calendar events on a paper field: the elapsed one solid tomato·11, the next one waiting in tomato·5. It is the app's identity wherever the OS asks for one — dock, launcher, Finder, About, the Linux window and notification. It always wears the idle composition: an app icon is an identity, not a state readout.

D19Generated, never drawn twice. Three hand-authored sources in context/mark/ (mark.svg, glyph-idle.svg, glyph-running.svg) carry classes and no fill attributes; scripts/gen-icons.mjs injects the palette from design.tokens.json and rasterizes every size — the D02 contract, applied to assets. Three palettes, because the backdrop differs: app paints on paper; panel paints on an unknown Linux panel, so it drops the pale tint (invisible on a light panel) for the brighter tomato·9 at 38% alpha, which survives light and dark alike; template is alpha-only black, since macOS discards a template image's colour and recolours it per menu-bar appearance. The rendered PNGs are committed, not built — rasterizing needs Chromium, which the build path does not have.

D20The glyph pair. The tray drops the field — at 16pt the enclosing square costs the bars half their height. Idle is the two bars; running fuses them into one unbroken block. The two glyphs occupy an identical bounding box, so the menu bar never shifts when the timer starts. The state reads as shape, which is what lets it survive a template image and satisfy A05 without a word beside it. On macOS the count-up title rides alongside; on Linux the glyph is the whole signal, so the glyph — not the title — is what must carry it.

D21Floors that do and don't apply. The mark is a brand asset, not text and not an icon-only affordance: A01 and A02 do not govern the contrast between its own bars (a recorded exemption below, matching WCAG's logotype carve-out). What does bind is A05 — and the glyph pair meets it by shape, not by hue.
