Process & Verification Requirements · v1

prd.html specifies the product; this specifies the apparatus that proves it. These are SDLC requirements — properties the build, CI, and acceptance system must hold — a different kind of claim from the application requirements, and until now without a home.

Read with acceptance.html, which routes each requirement to the method that proves it. That decides which notation; this constrains how the resulting guard must behave. A violation is a false green, not a user-visible bug, and is orthogonal to the five AC methods: a correct GOLD test can still violate these by running too late or being unprotected. The primary reader is the agent session doing the work (§03): process that lives only in CI config, code comments, or habit cannot bind a fresh session, so it lives here — the repo describes its own construction.

01 Scope

Two kinds of requirement

The four spec docs (concept, prd, glossary, acceptance) describe the application. This describes the process. The split:

Application requirementProcess requirement
What the product does. Lives in prd.html, proven per acceptance.html.How it is built, verified, released. Lives here.
"At most one timer is open" (§04)."A release-gating check runs on the PR, not post-merge."
A defect is wrong behavior the user sees.A defect is a false green — the gate passed when it shouldn't.
02 Requirements

The principles

Each is normative. The reference names the concern that motivated it; the first surfaced from the release-packaging failure (the pack job failed on every merge with spawn … app-builder ENOENT while CI stayed green), and the later ones generalize the same discipline to the offline guarantee, evidence integrity, build-time source transforms, the source census that measures the codebase, how visual style is verified, how the docs themselves speak about change, and how the process itself is encoded.

  1. Green is meaningful. A passing check must cover every concern its presence implies; a gate with a blind spot is a false guarantee, worse than none because it reassures. (§19 R01: packaging was broken while CI was green — no check exercised it.)
  2. Verify before the gate. A check that runs only after the merge it protects cannot prevent a regression, only discover it. Every release-gating concern has a check on the PR path. (§19 R01: the real pack ran post-merge only.)
  3. Mirror every manual check. Each MANUAL runbook step has a cheap automated guard over its invariant — a static assertion or a smoke run — so the common regression fails CI, not the next manual pass. (build-matrix.test.ts; the pack-smoke job.)
  4. Self-heal or fail loud. A guard recovers a known-recoverable fault; otherwise it fails at the boundary with a specific, actionable message, never a cryptic downstream error. (packaging guard reinstalls a missing native helper, else names the absent binary.)
  5. Protect the guard. A guard is code: it can be deleted, disabled, or rot. Assert that it stays wired, so removing it is itself a caught regression. (build-matrix.test.ts asserts pack-smoke + verify:packaging remain.)
  6. Fix to the cause; record the residue. When a failure's mechanism is unproven, prefer a fix robust to the cause over one betting on a single mechanism, and document what stays uncertain rather than implying certainty.
  7. The offline guarantee has a backstop. The product makes no network connection except the user-initiated update check (§17 R09, §19 R03); an automated check asserts this across every shipped surface — including assets that ship outside packages/*/src — and asserts production dependencies stay within a reviewed minimal allowlist. The check's own coverage is asserted, so a newly shipped surface cannot silently escape it. (§17 R09: the offline promise is load-bearing and otherwise only manually confirmable.)
  8. Regenerated evidence must not drift where it is deterministic. Any check that regenerates byte-reproducible acceptance evidence asserts the result is identical to what is committed and fails on any difference; evidence regenerated but never compared is a false green. Evidence whose bytes are not reproducible across environments — rendered screenshots, which shift with the Chromium/font stack — is regenerated and captured for review, never byte-gated: pinning it trades a false green for a standing false red. The line is determinism, not medium. (The clock-pinned CLI transcript and the fixture-clock-pinned judge report are diff-gated in CI; screenshots feed the by-eye comparison of R11.)
  9. Build-time source transforms are idempotent and fail loud. A step that rewrites source as part of the build — such as stamping the version (§19 R06) — must be safe to re-run without changing the result, and must abort with an actionable error if the target it expects is absent, never silently leave the source untransformed. (A silent no-op ships an unstamped or stale build.)
  10. The codebase census is exhaustive and reconciles. Any tool that measures the source — SLOC, documentation, per-category breakdowns — classifies every tracked file with no catch-all bucket, and asserts its arithmetic reconciles: each file's lines sum to its parts, the parts sum to the whole, and files counted equals files tracked. A new directory or unforeseen file matches nothing and fails the run rather than vanishing from the tally; a total that does not add up fails rather than misleading. The report is generated, never committed, so it cannot drift from the tree it describes. (scripts/sloc-report.mjs, gated by --check in CI. A measurement that quietly drops files or fudges its sums is a false green of a subtler kind — it reassures with a number that is wrong.)
  11. The mockups are the source of truth for style. The prototypes in context/mockups/ (and the design system they share) define the app's visual style; the renderer conforms to them, not the reverse. Style is therefore verified by looking — comparing rendered output to the mock, by eye or by an LLM over the captured screenshots — never by pinning CSS in source assertions (exact px, hex, or token usage on named selectors). Such pins fight every restyle and prove nothing about how the app looks: a green that survives an ugly screen is a false green of presentation. The deterministic gates stay on behavior, structure, and parity; the acceptance harness captures the screenshots the visual comparison reads. (§12/§18; issue #25 — code-pinned style checks were removed for exactly this reason.)
  12. The docs are timeless. A requirement or spec doc describes the present as if it had always been this way. Change narrative — "new", "changed", "previously", "no longer", transition notes, status remarks that lag what shipped — does not belong in the doc: it dates the moment the next change lands, and a stale note reads as current specification. History lives in git, where every prior state is recoverable with its date and reason. Artifacts that map an old state to a new one — a requirements-transition work-list, renamed *-old.html docs — are scaffolding of the change, not spec: they exist while the change is carried out and are deleted when consumed. (A lingering change-note is the spec's false green — it reassures the reader with text about a product that no longer exists; the old→new swap (§Z) that ends a requirements change deletes its own scaffolding for exactly this reason.)
  13. Procedure is prose; judgment stays in the operator. A repeatable multi-step process is specified as a skill — versioned prose an agent session reads and follows — never compiled into an orchestration script. A script fixes control flow at authoring time, freezing every judgment call at the moment it was least informed; the run-time state of the tree — what failed, what a review found — is what should steer the next step. Determinism belongs in the gates a procedure invokes, not in the driver. And a per-change script is scaffolding by construction: consumed by its one run, it lingers as process knowledge compiled into code nobody will run again (R12). (issue #46: the per-change agent-workflow scripts were retired in favor of the standing skills in §03.)
03 Execution

The agentic process

Stint is built by agent sessions, and the procedures they follow are specified the way everything else here is specified: as reviewable prose (R13). A skill (.claude/skills/*/SKILL.md) is a versioned Markdown procedure the session loads and follows — the process twin of a requirement doc. The session holds the run-time judgment between stages; the deterministic gates (npm test, the judge, the evidence-drift comparison, the no-network backstop) supply the certainty.

The requirements-change skills

SkillRole
change-requirementsAuthor. Grills the design one question-cluster at a time, then authors the transition artifact set — renamed *-old.html docs, new docs, the requirements-transition.md work-list, mockups for every new/changed GUI requirement — and stops. It never executes.
requirements-transitionExecute. Consumes the work-list, driving the change to one aggregated PR by following the staged, gated procedure the skill defines — the stages live in the skill, not restated here (§04's one-home rule). The merge is the human gate.

The pair is asymmetric: authoring wants a conversation (recommendations, sign-off, a synthesis the user approves), execution wants a checklist with gates. A change that needs a stage the execution skill lacks extends the skill itself — never a per-change fork. This pair carries application requirement changes — they are not the whole skill set (the discovery and triage skills live with the practice they serve, §06) — and changing this doc is lighter still (§07).

Subagents and model level

The session fans work out to subagents, each run at a chosen model level (capability tier). The selection rule is the gate question: if this subagent does its job subtly wrong, what catches it? A task whose subtle failure a deterministic gate catches — the build, a golden, the judge, a later stage that mechanically rechecks — may run at a cheap level; a task whose failure only a review or a human would notice runs at the strongest. Model level is set by what the gates cannot catch, never by task size; the default is the strongest available, and downgrading is a deliberate act. The operational rubric — which task kinds are downgrade-eligible, which never are — lives in the requirements-transition skill beside the stages that apply it.

04 Authoring

Authoring rules

Bind every doc in the repo: the context/ specs, the skills, README.md, CLAUDE.md.

  • Concise over grammatical. Scannability wins; fragments are fine. Cut every word that doesn't change what the reader does.
  • Common language. Use the ordinary word. Coin a term only when no common one fits — then define it in a glossary with its rejected synonyms. Invented terminology is a cost paid on every future read.
  • No editorializing. No hyperbole, no reassurance copy, no prose flourish. These are engineering documents: claims, reasons, tables.
  • Stateless. Present tense, as if it had always been this way — no change narrative, no responses to dead decisions (R12). History lives in git. One exception: a principle may cite the incident that motivated it.
  • One home per fact. State a fact in the doc that owns it; everywhere else, point. Duplicated rationale drifts — CI config and code comments keep the mechanics and point here for the why.
  • Mark the tier. A convention-tier statement appears under a "Recorded conventions" label in its owning section and is registered in §08's members row. Unlabeled prose in a requirements doc reads as requirement — the tiers stay decidable without asking the author.

Recorded conventions (reasoned, not binding — §08):

  • The prose specs are styled HTML. The context/ docs (concept, prd, glossary, acceptance, process, architecture) are authored as single, self-contained .html files, not Markdown. A spec is a designed artifact — a type ramp, tables, colour tokens, a masthead — read as a rendered page and carrying the mockups' visual language, which Markdown cannot hold; one file styles itself with no build step and no external asset, and renders the same wherever a browser opens it. This is why a skill is Markdown (§03) while a spec is not: the artifacts differ, so their format does. The cost is that the docs render as raw source on GitHub / mobile, so sharing a rendered page wraps the raw URL with htmlpreview — that workaround, and its known-broken outer-https variant, live in CLAUDE.md.
05 Enforcement

Automatic vs manual

The boundary rule: a check is manual only where headless CI physically cannot reach — live network, a real desktop OS, real wall-clock/power events, or the live Actions run itself. Any other manual check is a process defect. Every manual check keeps a cheap automated mirror (R03).

Automatic — every PR and merge to main ci.yml

The judge job also emits the screenshots/ tree; those bytes are not reproducible across the Chromium/font stack, so they are regenerated and uploaded as a build artifact for the by-eye/LLM style comparison (R11), never drift-gated — the R08 gate covers only the byte-reproducible text evidence, the CLI transcript and the judge report.

Post-merge (release.yml): stamp the date version (§19 R06) → pack macOS + Linux → publish the GitHub Release (§19 R05). The two PR-path pack-smoke jobs exercise an unpacked --dir pack on each OS; the full distributable build (.dmg, AppImage/.deb) is first exercised here, post-merge — an acknowledged residue. If a mac- or .dmg-only packaging breakage ever reddens a release, the escalation is full (non---dir) builds for both platforms on the PR path. Operator-run per GUI change, not CI-gating: the §W recording GIFs (npm run record) — QA evidence, regenerated so every committed GIF shows the current UI.

06 Discovery

Discovery

The §05 apparatus proves known requirements; discovery finds what nobody wrote a requirement about — defects in the product, and problems in the systems that build and verify it. Three instruments, one downstream. A discovery run gates nothing and produces no green: its output is issues. That is why this section binds at convention tier (§08), not requirement — skipping discovery cannot produce a false green.

the product                                  the systems that build & verify it

QA discovery

A discovery sweep drives the running GUI the way a user would — diverse flows, realistic seeded data — and files what it finds. The instrument is the QA driver (packages/gui/qa/): the real renderer in headless Chromium over a real @stint/core store, bridged by a port of the main process's IPC handler map, with a cursor/ripple/toast overlay (cine.mjs) for annotated recordings. The port is where a false finding could breed, so it is guarded apparatus (R05): a test binds its handler set to the IPC channel set, and a new channel fails the build until the driver learns it. Three skills carry the practice — qa-sweep (driving the GUI as a user to surface the defects, guided by coverage/tour/oracle heuristics), qa-gif-authoring (annotated screen recordings, also used wherever a recording is the artifact), and bug-report-authoring (turning a reproduced defect into an issue). The recurring find is a renderer-behavior bug the surface-neutral suites (core + tt, no DOM) cannot see; its durable guard is a JUDGE recipe (§05) driving the real renderer to an outcome — the same instrument the sweep uses.

Architecture review

The architecture review (arch-review) is the same idea aimed at the other target: an adversarial skeptic/researcher critique of the four systems that carry the requirements — the code, the verification apparatus, the SDLC, the context/ docs as artifacts — never the requirements themselves. The owner is grilled over every verdict; each problem that survives is filed as one issue: the problem in one sentence, evidence, stakes, severity and confidence. Problem capture only — the grilling confirms the problem; it deliberately decides nothing about the fix.

Sync assessment

The sync assessment (sync-assessment) is the standing instrument that asks whether the docs still tell the truth about the tree. Machine-decidable sync facts — a cited path exists, banned markup stays absent — are static-check territory; the assessment owns the judgment half: whether requirement text, coverage-row verdicts, and shipped behavior still agree, in either direction. A doc claiming more than the tree holds is a false green in prose; one claiming less sends readers to re-fix finished work. The run is heavy by design — fanned-out per-section readers over the whole claim surface (context/, acceptance/criteria/, the front doors), behavioral evidence through the QA driver where reading cannot settle a claim — and each finding routes by which side is wrong: shipped behavior diverging from a correct requirement files as a QA-discovery bug report; stale doc text files as an arch-review-style problem issue. Same posture as the other two instruments: no green, no fixes — issues, into the same triage gates.

Triage — the shared gate

Both streams converge on triage, the gate between a filed finding and workable backlog (triage-qa-findings / triage-arch-findings). Per issue, one comment records the category — a violated requirement, a missing one, or a plain bug, classified against the doc that owns the behavior (prd.html for the product, this doc for the process), with a label per category that applies — plus the owner decisions, the proof-of-fix plan at real files, and a routing verdict. The Triaged label is a contract: decisions settled, plan named, sized for one issue-anchored PR. process-triaged-issues drives the Triaged backlog to open PRs (§07; the merge stays the human gate); findings too large for one PR route instead to the requirements-change skills (§03) or a dedicated session — the routing verdict names which. A fix that modifies a deterministic gate is flagged at triage: the gate question (§03) cannot vouch for a subagent modifying the gate that would check it.

Recorded conventions (reasoned, not binding — §08):

  • One standalone issue per finding, labeled for its stream — Agentic QA Discovery: symptom, root cause with file:line pointers, honest severity and confidence, embedded repro evidence; Agentic Arch Review Discovery: problem, evidence, stakes, severity and confidence, no solution sections.
  • Repro evidence lives on the qa-evidence branch — an orphan branch, never merged, one issue-N/ directory per issue, embedded by raw URL. Never under acceptance/evidence/: that tree is generated proof, its text evidence drift-gated (R08); repro evidence is hand-captured and disposable (§09).
  • Each issue names its evidence directory so it can be pruned after the issue closes.
  • Sweep recipes are scratch. The driver is committed apparatus; the per-sweep scripts that steer it are consumed by the run, like any scaffolding (R12).
  • The sync assessment runs once in a while. No fixed cadence — run it after a stretch of landed change large enough to strain the docs, before an arch review, or when a doc is caught wrong. Skipping a run cannot produce a false green (its output is issues), which is why the cadence is convention, not requirement.
07 Governance

Branch, PR, release

Requirements:

  • Every change rides a PR. Issue-anchored branch → ready (not draft) PR → owner merge. No direct pushes to main. The merge is the one human gate (§03).
  • Merge on green only. The §05 per-PR checks pass before merge; a red check blocks.
  • Every merge to main is a release. release.yml publishes a GitHub Release versioned YYYY.M.D[.N] with the macOS + Linux artifacts. Two reasons: a release path that runs on every merge cannot rot unseen (R02), and shipping is fast by default. A failed release surfaces through GitHub's own workflow-failure email to the repository owner — owner-configured, out-of-repo; an acknowledged residue, not an in-repo gated guarantee (there is deliberately no alerting step in release.yml).
  • Changing this doc. Process requirements change by grilled PR: interrogate intent before authoring, author directly, merge gates. None of the transition machinery applies — no *-old.html coexistence, no work-list, no swap; there is no generated evidence to migrate.

Recorded conventions (reasoned, not binding — §08):

  • Merge commits, no squash — keeps wave checkpoint commits reachable for bisect.
  • Branch names come from the tooling and carry the issue number.
  • Commit messages: imperative subject naming the issue; co-author + session trailers.
  • One issue per change.
08 Line

Specified vs convention

The tier test: can violating it produce a false green, lose data, or break a shipped promise? → requirement. Has a reason worth keeping, but violation is visible and cheap to reverse? → recorded convention. Otherwise → unspecified, on purpose.

TierMembers
requirementThe principles (§02); the agentic process + skills (§03); authoring rules (§04); the automatic/manual boundary + inventory (§05); the QA-driver parity guard (§06); PR-gated main, merge-on-green, release-per-merge, the process-change rule (§07).
recorded conventionThe styled-HTML spec-doc format (§04). Merge commits; tooling branch names; commit-message shape; one issue per change (§07). The discovery conventions (§06): one labeled issue per finding, the triage comment-and-label contract, the qa-evidence branch, per-issue evidence directories with prune-after-close, scratch sweep recipes, the periodic sync-assessment run.
unspecifiedCode style beyond the linter; PR body shape; issue formatting; anything not named in this doc. Absence is information: an unnamed practice is at most convention.
09 Words

Process glossary

The SDLC twin of glossary.html: one canonical term per process concept.

TermMeaning
gateA check that blocks the path it protects (the PR, the release) when red. A check that merely reports is not a gate.
guardThe automated mirror of a concern otherwise confirmed by hand; makes the common regression fail CI instead of the next manual pass (R03).
backstopThe guard of last resort behind a promise otherwise held only by convention — the no-network check (R07).
false greenThe process defect: a gate passed while a concern its green implies went unchecked (R01).
smokeA cheap end-to-end run proving a path is alive, not that it is correct — pack-smoke.
runbookThe ordered procedures for the manual checks (acceptance/criteria/manual/runbook.md); each has an automated mirror (R03), and §05 lists the live residue a human must run.
self-healA guard recovering a known-recoverable fault itself; anything else fails loud at the boundary (R04).
safety valveA deliberate, visible manual bypass of an automated gate (a workflow_dispatch re-run, a runbook override) — allowed, recorded, never silent.
criteriaHand-authored statements of what must hold (acceptance/criteria/). Reviewed, never generated.
evidenceGenerated proof the criteria hold (acceptance/evidence/). Regenerated by the suites; the byte-reproducible text (CLI transcript, judge report) is compared against what is committed and fails on any drift (R08), while screenshots are regenerated for review; never hand-edited. Distinct from repro evidence.
surfaceAnything shipped that a promise must hold over: the CLI, the GUI, assets outside packages/*/src.
parityThe requirement that both surfaces expose the same capability over the same core.
skillA versioned prose procedure under .claude/skills/ that an agent session follows; the unit of process (R13). Rejected: workflow — that word now names GitHub Actions (.github/workflows/) only.
operatorThe agent session following a skill; holds the run-time judgment between gates.
subagentA scoped agent the operator spawns for one unit of work; owns its declared files for the duration of its wave.
model levelThe capability tier a subagent runs at; chosen by the gate question (§03), never by task size.
waveA set of file-disjoint work units executed in parallel, verified green and checkpointed before the next begins.
checkpointThe per-wave commit that keeps a long run resumable and bisectable.
work-listrequirements-transition.md — the map from old spec to new that the transition consumes; scaffolding.
scaffoldingAn artifact that exists only while a change is carried out and is deleted when consumed (R12): the work-list, the *-old.html docs.
swapA transition's gated final stage: old docs and scaffolding deleted, front-door docs updated — inside the same PR, whose merge is the human gate.
sweepOne QA-discovery run (§06): drive the GUI as a user over realistic data, file the findings. Produces issues, never a green.
arch reviewOne architecture-review run (§06): adversarial critique of the systems that build and verify the product, verdicts grilled with the owner, confirmed problems filed. Produces issues, never a green — and never a fix.
sync assessmentOne requirements↔implementation synchronization run (§06): judge whether the docs still describe the tree and its behavior, file each drift finding into the discovery stream that owns it. Produces issues, never a green — and never an edit.
findingWhat discovery surfaces, filed as one labeled issue (§06): a sweep's reproduced, root-caused defect, or a review's confirmed problem; the sync assessment files its drift findings in whichever of those forms fits. Not a requirement failure until someone writes the requirement.
triageThe gate between a filed finding and workable backlog (§06): category, owner decisions, proof-of-fix plan, routing verdict — one comment, then the Triaged label. The label is a contract, not a status.
repro evidenceHand-captured recordings/screenshots embedded in a finding's issue; lives on the qa-evidence branch, prunable after close (§06). Not evidence — never under acceptance/evidence/, never drift-compared.
10 Map

Where requirements & context live

CLAUDE.md's Files table is the front door.

Under acceptance/ the two halves of the AC apparatus are kept apart: criteria/ holds the acceptance criteria (what must hold — the rubric, schemas, parity matrix, runbook, and coverage map), and evidence/ holds the acceptance-criteria satisfaction evidence (the generated proof those criteria hold).
